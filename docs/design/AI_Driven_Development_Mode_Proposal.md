# 备至智洗平台：AI 驱动的企业级持续开发模式可行性分析与落地方案

> 面向当前文档体系（Req / Des / UI-SVG / Files / Codex 提示语与脚本）的“可持续、可增量、可自动化、可端到端验收”研发方法。

## 1. 结论先行（TL;DR）

你提出的模式**可行**，但要从“文档链路自动化”升级为“**文档 + 可执行规格 + 持续验证**”三位一体：

1. **文档持续产出**：Req→Des→UI→Files→Prompt/Script 这条链保留；
2. **规格可执行化**：将关键需求沉淀为可机读的契约（OpenAPI、事件 Schema、状态机、权限矩阵、测试用例）；
3. **端到端持续验收**：每次增量变更自动触发“契约测试 + 集成测试 + E2E 回归 + 数据一致性校验”。

只有这样，才能避免“前后端分别很完整但拼不起来”的常见问题。

---

## 2. 你当前模式的价值与风险

### 2.1 价值（你已经做对的部分）

- 以需求文档为源头，形成版本化资产（v1、v2…）；
- 强调“增量更新”而非推倒重来；
- 要求 AI 同时输出提示语与脚本，具备自动化潜力；
- 有 UI 高保真与接口文档，具备跨角色协作基础。

### 2.2 核心风险（若不治理会卡住）

1. **文档漂移（Doc Drift）**  
   Req、Des、UI、Files 分别演进，但缺少“单一真相源（SSOT）”与自动一致性检查。

2. **前后端契约断裂（Contract Gap）**  
   前端按页面理解开发，后端按接口文档开发，最终字段、状态机、错误码、幂等语义不一致。

3. **“看起来自动化”但不可复现**  
   Prompt 每次手工拼接，输出受上下文影响大，无法稳定复跑。

4. **增量不可追踪**  
   仅在自然语言标注“v1+v2”，但没有结构化 diff 与影响分析。

5. **端到端质量缺口**  
   缺少真实业务链路验收（如下单→派单→履约→分润→对账），上线后才暴露流程断点。

---

## 3. 推荐的“企业可用”开发模式（V 模型 + AI 工厂化）

将现有模式升级为 **6 层资产 + 4 条流水线**。

## 3.1 六层资产（都要版本化）

1. **L1 业务需求层（Req）**  
   业务目标、范围、角色、流程、规则、NFR。

2. **L2 设计层（Des）**  
   架构、领域模型、状态机、模块边界、异常策略。

3. **L3 体验层（UI-SVG + 设计令牌）**  
   页面结构、组件规范、交互状态、可访问性。

4. **L4 可执行规格层（关键新增）**  
   - OpenAPI（REST）
   - AsyncAPI/事件 Schema（消息）
   - 状态机定义（YAML/JSON）
   - 权限矩阵（RBAC）
   - 核心业务规则（可测试表达式）

5. **L5 实现层（代码 + Prompt + 脚本）**  
   Codex 提示语模板、脚本编排、代码生成/修改记录。

6. **L6 验证层（测试与观测）**  
   单测、契约测试、集成测试、E2E、回归数据集、SLO 监控。

> 关键原则：L4 才是前后端协同的“硬连接器”。

## 3.2 四条流水线

### A. 文档生成流水线（Authoring Pipeline）
Req 变更后自动生成：Des 草案、UI 草案、接口草案、变更清单。

### B. 规格同步流水线（Spec Sync Pipeline）
自动检查 Req/Des 与 OpenAPI/状态机/权限矩阵一致性，阻断不一致提交。

### C. 代码实现流水线（Implementation Pipeline）
基于规格与 Prompt 模板生成改动，必须附带测试与迁移脚本。

### D. 验证发布流水线（Verification & Release Pipeline）
自动执行：契约测试→集成→E2E→回归→灰度发布→指标守护。

## 4. 增量版本机制（v1→v2）如何设计才“快且稳”

建议把“文档版本号”扩展为“**变更包（Change Pack）**”机制。

每次 Req-vN 变更产出一个 `CP-N`，至少包含：

1. `change_summary.md`：业务变更摘要；
2. `impacted_modules.yaml`：影响模块图（前端页面、后端服务、任务、数据表、事件）；
3. `api_diff.yaml`：接口 diff（新增/删除/破坏性变更）；
4. `state_machine_diff.yaml`：状态流转变更；
5. `test_plan_delta.md`：新增/修改回归点；
6. `prompt_delta.md`：给 Codex 的增量提示语。

这样你可以做到：
- 快速评估改动范围；
- 自动选择回归测试子集；
- 明确是否允许破坏性变更。

---

## 5. 端到端落地保障（避免前后端孤立）

下面这些机制是“必须项”：

1. **契约先行（Contract-First）**  
   前后端都从 OpenAPI/Schema 生成类型与桩代码，禁止手写漂移字段。

2. **Mock + 沙箱联调**  
   接口未完成前，前端依赖契约 Mock；后端完成后做契约回放对比。

3. **真实业务剧本 E2E**  
   至少维护 10~20 条黄金路径剧本（含异常路径），每次变更必跑。

4. **测试金字塔 + 变更感知回归**  
   小改跑局部，大改跑全量；由 `impacted_modules.yaml` 自动决定测试范围。

5. **数据一致性与账务对账校验**  
   对分润、结算、退款等建立离线核对任务，防止“流程通了但账错了”。

6. **可观测性验收门禁**  
   发布不仅看测试通过，还看关键 SLI（成功率、延迟、错误率、消息堆积）。

## 6. AI 提示语与脚本建议（手动版 + 全自动版）

## 6.1 手动验证版（Human-in-the-loop）

适合早期探索：
- 步骤 1：输入 Req-vN + 上一版基线；
- 步骤 2：AI 输出 Des/UI/Files 草案；
- 步骤 3：人工审核并确认变更包 CP-N；
- 步骤 4：AI 依据 CP-N 生成代码与测试；
- 步骤 5：人工验收关键流程后合并。

优点：风险可控。缺点：速度中等。

## 6.2 全自动版（Pipeline-driven）

适合中后期稳定期：
- Git 触发器检测 `Req` 目录变化；
- 自动生成 CP-N 与规格 diff；
- 自动生成代码分支与测试；
- 自动运行 CI 全链路验证；
- 通过策略门禁后自动发起 PR。

优点：速度快、可规模化。缺点：需前期治理投入高。

## 7. 推荐的组织与角色分工

- **产品/业务（Owner of Req）**：维护需求事实与验收口径；
- **架构/技术负责人（Owner of Spec）**：维护可执行规格与兼容策略；
- **前后端团队（Owner of Implementation）**：按契约交付；
- **QA/运维（Owner of Verification）**：维护 E2E 场景与发布门禁；
- **AI 工程负责人（Owner of PromptOps）**：维护提示语模板、评估指标、失败回放库。

---

## 8. 三阶段实施路线图（建议）

### Phase 1（2~4 周）：打地基
- 固化文档目录与命名；
- 建立 OpenAPI/状态机/权限矩阵三件套；
- 接入最小 CI：格式检查 + 契约检查 + 冒烟 E2E。

### Phase 2（4~8 周）：增量自动化
- 建立 Change Pack 自动生成；
- 引入 impacted-based 回归选择；
- 规范 Prompt 模板与脚本参数化。

### Phase 3（8~12 周）：全自动闭环
- 自动分支与 PR 机器人；
- 灰度发布与指标回滚自动化；
- AI 输出质量看板（成功率、返工率、平均修复时长）。

---

## 9. 关键 KPI（判断模式是否成功）

- 需求到上线 lead time（中位数）；
- 变更失败率（CFR）；
- 回滚率；
- 需求变更后 48 小时内完成率；
- 前后端联调缺陷密度；
- 文档与代码一致性通过率（spec conformance）。

---

## 10. 一句话建议

你的方向是对的，但要把“AI 生成很多文档”升级为“**AI 驱动可执行规格 + 自动化验证门禁**”。

只有当每次增量都能自动回答这三个问题，模式才真正企业可用：
1. 改了什么（Diff）？
2. 会影响哪里（Impact）？
3. 是否仍然端到端正确（E2E Proof）？
